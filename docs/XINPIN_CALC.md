## 2. 方案 ④：Edge Function `xinpin-tuiguang-calc`

- 代码：`supabase/functions/xinpin-tuiguang-calc/index.ts`（鉴权）+ `_shared/xinpin-run.ts`（编排）+ `_shared/xinpin-calc.ts`（纯计算）。
- `mode=dryrun` 逐格对比公式值，返回 `[cell, formula_value, script_value]`；`mode=write` 用 values_batch_update 回写；默认目标 sheet「新品推广-脚本」「产品推广计划-脚本」；写源表必须 `confirm_source_write`=源表 token。
- 统计格判定：第 3 行「寄样数量 / 返素材数量 / 剪辑素材数量」所在列中，原来有统计公式的格；公式换成数值后改认「这格已有值」（新品推广新加行需整行复制上一行），产品推广计划按「G 站点属于该同事负责站点（新品推广第 2 行）」判定。
- 剪辑台账来源：请求 `clip_sheet` → 原公式 IMPORTRANGE 链接 → env `XINPIN_CLIP_SPREADSHEET` → 默认 `EHmlsMg33heiiOtb4kZcvpg8nJg`；读不到报错，不静默写「无素材」。
- 读建联表用 sheet 的 row_count 封顶（shared readRange 开放区间遇 1200+ 连续空行会提前停，林乐欣表有 1468 行空档）。
- 定时：`xinpin-calc-hourly`（每小时 :25，migration `20261128140000`，**建好即停用**）→ `/api/public/hooks/xinpin-calc-cron`；失败发飞书。
- 环境变量：`XINPIN_DATA_SPREADSHEET`（数据来源表）、`XINPIN_TARGET_SPREADSHEET`（回写表），cron 只认环境变量。

## 3. 实测结果（复制表，2026-11-28）

### 3.1 一致率
| 对比 | 新品推广 | 产品推广计划 |
|---|---|---|
| ④ vs 原公式值 | 683/746 一致；63 格不一致**全部是寄样列、全部由去重造成**（按不去重复刻 63/63 = 公式值；这 63 格原 965 → 去重 658） | 620/620 |
| ④ vs ①（同为去重口径） | 606/606 | 596/596 |
| ④ TS vs 独立 Python 实现 | 每列合计全等；按站点合计之和 = 列合计 | — |

过程中发现并修正：① 最初把 SKU 按「数字段」归一（`,3120,3121,`），会把 `3120-K+3121-K` 也算进 SKU `3120+3121`，原公式正则不算 → 改为把每个数字段包成 `<…>` 再做通配匹配，与正则逐格等价。

### 3.2 重算耗时（改建联-李汝华一行 → API 读到统计格的值；飞书重算期间返回 90235 Data not ready）
| 场景 | 3 次 | 中位数 |
|---|---|---|
| 现状：U 列 + 原 INDIRECT 公式 | ≈990（40 秒粒度）/ 870 / 920 秒 | **920 秒** |
| ① 只优化两张推广表（U 列保留） | 864 / 937 / 910 秒 | **910 秒** |
| U 列换成数值 + ① | 18.8 / 18.9 / 17.8 秒 | 18.8 秒 |
| U 列换成数值 + 原 INDIRECT 公式 | 13.0 / 13.5 / 13.5 秒 | 13.5 秒 |
| U 列换成数值 + 两表无统计公式（④ 终态） | 6.6 / 6.8 秒（2 次） | — |

结论：瓶颈是 7 张建联表 **U 列（38,702 个单元格，每格扫建联动态汇总 3 列 × 50,914 行）**，不是两张推广表。① 的辅助列（6 表 × 8 列 ≈ 30 万个公式，含 MATCH 首次出现判断）本身还比原公式慢。

### 3.3 方案④ 单次运行
本地 node 跑同一份代码（未部署到 Supabase）：34～44 秒，飞书 API 170～173 次（6 张建联表 + 2 张剪辑表分块读 + 配置读 + 2 次 batch 写），建联表按 sheet 并发读。
