## 一、财务表 / 订单表 按天更新

### 决定
| 项 | 决定 |
|---|---|
| 更新频率 | 先按天（实现为每小时增量，回填完成后每轮只有几次接口调用） |
| 做在哪 | 取数接口与页面都在 ads-auth；`yunge008/finance-order` 只作口径与规则的**只读参考**，不改它 |
| 产出 | ①「全站点汇总」汇总表，**必须显示数据截止日期** ②「汇总数据回写」：**按月汇总，汇总行在最上方，日期行从近到远排序** |
| 店铺 | 先 PH、TH 测试，没问题后逐店接入（`tts_shops.daily_sync` 开关） |
| 对账 | 用**过去三个月**数据（2026-08 起）与手工导出表 + finance-order 结果逐列对比，0 差异才算通过 |
| 不漏项 | finance-order 页面内折叠说明（6 个 TAB）、`src/config/mappings.json`、计算代码（finance-analyze / order-parse / order-analyze / finance-attribution / summary-page 等）**三者对照**，逐项列清单，每项标「已实现 / 对账通过」 |

### 阶段
1. **入库**（1125.264 代码完成）：`tts-export kind=sync` + 路由 `/api/public/hooks/tts-sync-cron` + pg_cron `tts-daily-sync`（每小时第 17 分）。表：`tts_orders`（订单原文，按 update_time 增量覆盖）、`tts_finance_statements`、`tts_finance_tx`（结算交易原文）、`tts_sync_state`（进度、错误、未登记字段）。存接口原文（去空值/0），口径映射放在汇总计算层。接口出现口径表未登记、且非 0 的字段 → 记录并发飞书。
2. **口径清单 + 对账**：把 finance-order 全部取数/计算规则列成清单；API 数据按清单算出 PH、TH 三个月的结果，与手工表结果逐列对比。
   - 已知差异点：接口结算交易是订单维度，不带 SKU ID / 数量。拟沿用 finance-order 现有 PHL 规则「按订单号展开订单表 SKU 行，金额只挂第一条」——**须在对账中验证成本件数一致**，不一致再改为逐单拉 SKU 级明细。
   - 接口导出缺「订单创建时间」列：结算交易原文里取 `order_create_time`（已单独入库）。
3. **ads-auth 汇总页**：全站点汇总（截止日期）+ 汇总数据回写（按月汇总在上、日期行近→远），可写飞书。
4. **逐店接入**：每接一个店先跑该店三个月对账。

## 二、GMV MAX 归因数据自动抓取

### 决定
| 项 | 决定 |
|---|---|
| 手动上传 | **保留兜底** |
| 抓取范围 | 每月抓「该站点下所有有消耗的广告户」——换户当天新旧两户自然都在，不靠推断决定抓哪个户 |
| 换户判定 | 同一时刻一个站点只有一个广告户有消耗。按站点每天记录有 GMV MAX 消耗的广告户；**某天出现一个与当前户不同的户开始有消耗 = 换户日**（当天旧户是否也有消耗、旧户之前停了多久都不影响） |
| 飞书提醒 | ①换户 ②换户后旧户又出现消耗 ③**同一站点**同一天 ≥3 个户有消耗 ④某户有消耗，但在设置里没有启用该户 |
| 对账 | 与上传表逐站点比：花费/GMV/订单合计（差 < 0.01）、VID×商品集合两边差异明细、商品卡片与直播单独比、达人账号名与发布时间抽样逐值比。全部一致才切换 |
| 截断 | 上传表正好 10 万行的月份：负责人确认 10 万行之后基本都是 0，不算问题 |
| 对账工具 | 做成长期可用的轻量功能（例如每月抓取后自动与已上传的表对比、出差异报告），平时不跑、不拖慢页面；或做完后禁用。不得增加日常使用的复杂度 |

### 可行性依据
- 之前的每日同步已能从接口取到归因所需字段：VID（item_id）、达人账号（tt_account_name）、内容类型（shop_content_type）、发布时间、商品（item_group_id）、花费、GMV、订单数（见 `gmv-max-sync` Phase 3、`gmv_max_vid_meta`）。
- 之前暂停的直接原因是数据库容量；「接口数据与导出对不上」的具体差异没有留下记录，本次对账必须查清并写进本文。
